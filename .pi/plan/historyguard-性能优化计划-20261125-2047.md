# HistoryGuard 性能优化计划

## 目标与基线

在不改变规则语义、统计口径、存储格式、权限和界面外观的前提下，降低后台匹配开销和弹窗更新成本，缩短批量清理时间。继续保持零第三方运行时依赖。

已完成只读检查：
- 工作区初始无未提交改动。
- Node.js `v24.19.0`，`npm test` **21/21 通过**。
- 对每组 500 个 URL 预热后运行 3 次，取中位数：100 条规则未命中耗时 **107.54 ms**；1000 条规则未命中 **1177.91 ms**，命中最后一条 **1071.12 ms**。这是 Node 合成基准，不代表真实 Chrome 性能。

## 实施内容

### 1. 复用规则编译结果，URL 只解析一次
修改 [rules.js](D:/用户/桌面/js/historyGuard/lib/rules.js:198)：
- `findFirstMatchingRule` 每次查找只解析一次目标 URL，再逐条检查启用规则。
- 使用 `WeakMap` 按规则对象缓存编译结果，包括无效规则结果；检查规则文本，文本改变时重新编译，旧对象可自动回收。
- 保持 `matchRule` 的现有调用方式、规范化及匹配语义，继续返回列表中第一条启用且匹配的原始规则对象。
- 不缓存访问 URL，不向持久化状态写入正则或缓存数据。

### 2. 加速现有历史批量清理
修改 [background.js](D:/用户/桌面/js/historyGuard/background.js:177) 和 [state.js](D:/用户/桌面/js/historyGuard/lib/state.js:316)：
- 保留状态操作的串行队列，仅将批量历史删除改为固定 **4 路并发**，不一次性创建所有删除任务。
- 保留按 URL 去重、现有扫描范围和规则匹配顺序。
- 记录每次成功删除的完成时间，按规则汇总批次统计，避免每删除一条记录都遍历复制整个规则列表；失败不计数，跨日仍按本地日期重置今日统计。
- 批次完成后继续一次性保存最终状态。实时访问处理仍在删除成功后立即持久化，不引入延迟写入或定时刷新。

### 3. 去重图标更新
修改 [background.js](D:/用户/桌面/js/historyGuard/background.js:125)：
- 缓存成功设置的默认图标和各标签页图标状态，跳过相同状态的重复设置，并合并相同的进行中请求。
- URL、规则或总开关变化时重新判断应显示的状态；设置失败不记入成功缓存，后续可重试。
- 标签页关闭时清理对应缓存；Service Worker 冷启动时重新同步。
- 保留回调/Promise API 兼容及 `runtime.lastError` 的处理。

### 4. 弹窗按需渲染
修改 [popup.js](D:/用户/桌面/js/historyGuard/popup.js:503)：
- 跟踪当前页面和待更新状态，只渲染可见页面；隐藏的统计、规则及设置页面在下次切换时使用最新状态更新。
- 将全局状态和必要徽标更新从统计页渲染中分离，避免初次打开弹窗就排序统计、构建图表和统计明细。
- 编辑、取消编辑只刷新规则列表，不重建统计页面。
- 列表使用 `DocumentFragment` 一次提交，日期格式化复用一个 `Intl.DateTimeFormat`。
- 保留快捷添加、行内编辑、Enter/Esc、导入导出及统计页面切换行为。
